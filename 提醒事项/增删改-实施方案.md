# 给提醒事项加上「删除」和「修改」

> 2026-08-04。现状：**只能新增。** 本文是补齐删/改的完整方案。
> 仓库侧代码（`queue_client.py`）已写完并离线验证；剩下队列服务和快捷指令两处。

---

## 一、为什么现在删不了

`架构.md` 曾写 `POST /push` 的 `replace: true` 可以「覆盖已有同名条目」。
**这句话有误导性** —— 它覆盖的是**队列里还没被认领的记录**，不是手机上那条提醒。

根因在快捷指令：它整段只有一个动作 **「添加到收集桶」**，没有查找、没有移除。

```
入队 ──────► 队列排队 ──────► 快捷指令认领 ──────► 落进提醒事项 App
        ↑                  ↑                      ↑
   replace 在这段有效     认领的一刹那          过了这条线，
                                            队列侧再也碰不到它
```

所以要能删，**必须让快捷指令学会「查找 + 移除」**。这不需要 Mac —— 苹果快捷指令
自带「查找提醒事项」和「移除提醒事项」两个动作，第三代「无需常开机器」的前提保住了。

---

## 二、设计：加一段，不动老的

**做成一个独立的新快捷指令，不去改现有那个。**
新的这个就算完全是坏的，也伤不到新增链路 —— 两者互不相干，各自由「自动化」定时触发。

**不在循环里做 if/else 分支。** 那是快捷指令里最容易编错的部分，而且会跟现有
能跑的逻辑纠缠 —— 编坏了连新增一起废掉。改成**前面挂一段独立的删除块**：

```
① 获取  http://43.160.249.235:8787/claim-delete         ← 全新一段
② 重复每一项：
      查找提醒事项（列表 = 收集桶，标题 是 「重复项目」的 title）
      移除提醒事项（上一步的结果）
③ 结束重复
──────────────────────────────────────────────────────
④ 获取  http://43.160.249.235:8787/claim                ← 现有的，一个字不改
⑤ 重复每一项： …… 添加到 收集桶 ……
⑥ 结束重复
```

三个好处：

1. **没有分支**，快捷指令里最难编的部分完全避开。
2. **删除跑在新增前面** —— 「改期 = 先删后加」的顺序天然正确，不用额外协调。
3. **老的那段一个字不动** —— 新段编错了，你的新增链路照常工作，不会两头断。

## 三、队列服务要改什么（Clawbot 在 VPS 上做）

保持向后兼容：`/push` 和 `/claim` 还是那两个端点，只是加参数。**现有快捷指令
不改也能继续跑。**

| 端点 | 改动 |
|---|---|
| `POST /push` | 新增可选字段 `"op"`：`"add"`（默认）\| `"delete"`。缺省时行为与现在完全一致 |
| `GET /claim` | 不带参数时**只返回 `op=add` 的条目**（＝现有行为，务必保持） |
| `GET /claim-delete` | 新增。返回待删条目并出队，语义与 `/claim` 一致（认领即消费）。**`GET /claim?op=delete` 为等价写法，两者都要保留** |
| `POST /cancel` | 新增。body `{"title": "..."}`，把**尚未被认领**的条目从队列里撤掉，返回撤掉的条数 |

> ⚠️ **为什么是独立路径 `/claim-delete`，不是 `/claim?op=delete`。**
> 服务器认不出的**查询参数会被静默忽略**，于是 `?op=delete` 会当成普通 `/claim`，
> 把**待新增**的那批条目返回给删除段 —— 删除段拿着它们去「查找 + 移除」，
> 结果是排队等着写入手机的提醒被吃掉，且一条都没真加进去。
> 认不出的**路径**返回 404，删除段空转，无害。
> 这个差别决定了快捷指令能不能先于服务器安装。
>
> 2026-08-04 生产端**两种写法都实现了**。手机上的快捷指令一律用路径形式 ——
> 查询参数形式只在「服务器认识 `op`」的前提下成立，服务一旦重装或回滚就退化成
> 上面那个吃掉队列的失败模式；路径形式在任何旧版本上都只是 404。

**两条实现约束：**

- **`op=delete` 的条目和 `op=add` 的条目必须分开排队。** 若混在一个队列里，
  老版本快捷指令调 `/claim` 会把删除指令当成新增条目写进手机 —— 变成一条
  标题是待删事项的垃圾提醒。
- **删除条目只需要 `title` 字段**，`due` / `notes` 不参与匹配（手机那端是按标题找的）。

## 四、安全规则（**不要放宽**）

删除**不可撤销**，且手机那端只能按标题匹配 —— 没有 ID 能传回来。所以：

| 命中情况 | 行为 |
|---|---|
| 0 条 | 什么都不做，如实回报「没找到」 |
| ≥2 条 | 什么都不做，把候选全列出来让用户挑 |
| 1 条 | 用**设备上的原始标题**下指令，不用用户的转述 |

相似度阈值 **0.85**（比新增去重的 0.75 更严 —— 删错的代价高得多）。

**定位顺序：先查 `/pending`，再查 `/snapshot`。** 顺序反了会出现
「删除指令在设备上找不到东西、新增指令照样把它加进去」的净效果为零的 bug。

**执行前必须把 `exact_title` 念给用户确认。** 这条写进 `CLAUDE.md` 铁律。

## 五、仓库侧已完成

`queue_client.py` 新增：

| 函数 | 作用 |
|---|---|
| `locate(title)` | 先队列后设备定位，返回 `where` / `exact_title` / `candidates` |
| `delete(title)` | 在队列里 → `POST /cancel`；在设备上 → `POST /push {op:"delete"}` |
| `update(title, due=…, new_title=…)` | 在队列里 → `replace`；在设备上 → 先删后加 |
| `cancel(title)` | 撤回未认领条目 |

离线验证 10 项全通过：找不到不动手、唯一命中用原标题、多条命中拒绝执行、
未认领走 cancel、队列优先于设备、改期顺序正确（delete 在前）、改标题、
未认领改期走 replace、`force` 也删不了不存在的、相似度不足不误删。

## 五之二、生产端状态（2026-08-04，Clawbot 实测）

- ✅ `POST /push` 缺省 `op` 行为不变；`op=delete` 单独入队
- ✅ 两个队列**物理分离**：`queue.json`(add) / `delete_queue.json`(delete)
- ✅ `GET /pending` 看不到 delete 队列
- ✅ **`/claim` 不带参数只吐 add 队列** —— 老快捷指令不会把删除指令写成提醒
- ✅ `POST /cancel` 返回 `{"ok":true,"cancelled":N}`，`/pending` 复核已撤掉
- ✅ 非法 `op` 返回 400
- ✅ `/claim` 同时支持 GET 与 POST（生产原实现是 POST，规格写 GET，两者兼容）
- ⏳ `/claim-delete` 路径别名待补 —— 手机快捷指令用的是这个形式
