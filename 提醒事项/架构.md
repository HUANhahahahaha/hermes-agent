## 全链路

```
微信 Clawbot ──入队──▶  队列服务 43.160.249.235:8787
                              │
                              │  GET /claim  （快捷指令定期拉取并认领）
                              ▼
                    Apple 快捷指令（用户 iPhone）
                              │  解析 title / due / notes
                              ▼
                    提醒事项「收集桶」列表 ──▶ 用户看得到 ✅
```

## 快捷指令做了什么（截图逐条还原）

1. `获取 http://43.160.249.235:8787/claim 内容`
2. `重复 URL 的内容中的每一项`：
   - 取 `title` 的值
   - 取 `due` 的值
   - 取 `notes` 的值
   - `从字典值获取日期`（把 `due` 转成日期对象）
   - `将字典值添加到 收集桶（日期）` ← 写入提醒事项
3. `结束重复`
4. `停止并输出 重复结果`；无输出时不执行任何操作

## 队列返回的数据格式

`GET /claim` 返回一个数组，每项至少含三个字段：

```json
[
  {"title": "孙建亚老师 家前采时间确认", "due": "2026-07-02 10:00",
   "notes": "地点：绿洲比华利花园931号楼"}
]
```

- `/claim` 语义是**认领**：取走即出队，重复调用不会拿到同一条。
- ⚠️ **不要为了调试去 GET `/claim`** —— 会把待写入的条目消费掉，
  用户手机就再也收不到那几条了。

## 队列服务 API（2026-07-28 由用户经 Clawbot 确认）

**服务在 VPS 本机监听，Hermes 侧一律走 `http://127.0.0.1:8787`（不出公网）。**
公网 `43.160.249.235:8787` 那一面是给 iPhone 快捷指令 `GET /claim` 用的。

### 端点

| 端点 | 用途 | 安全性 |
|---|---|---|
| `GET /pending` | 查待写队列 | ✅ 只读，不消费 |
| `GET /snapshot` | 查 Mac 端上传的**设备提醒快照** | ✅ 只读，不消费 |
| `POST /push` | 真正入队 | ✍️ 写入 |
| `GET /claim` | 快捷指令认领出队 | ⛔️ **消费型，禁止用于调试/查询** |

### 请求头
```
X-Queue-Token: <token>
Content-Type: application/json
```

### 鉴权
Token 存在**文件** `~/.reminder-queue/token`（**不是环境变量**）。
读取该文件取值，不要把 token 写进代码或本仓库。

### `POST /push` 请求体
```json
{
  "title":   "孙建亚老师 家前采时间确认",
  "due":     "2026-07-02 10:00",
  "remind":  "2026-07-02 09:00",
  "list":    "收集桶",
  "notes":   "人物：孙建亚老师｜地点：绿洲比华利花园931号楼",
  "source":  "hermes-vps",
  "replace": false
}
```

- `due` 到期时间，`remind` 提前提醒时间（两者独立）
- `replace` 为 `true` 时覆盖已有同名条目，用于「改期」场景

## 写入前的去重 / 冲突协议（必须照做）

**不要拿到内容就直接 POST。** 既有流程是三步：

1. **`GET /pending`** —— 与队列中待写条目比对，防止重复入队。
2. **`GET /snapshot`** —— 与**设备上已存在的提醒**比对：
   - 标题相似度用 `difflib.SequenceMatcher`，**阈值 ≥ 0.75** 视为同一件事
   - 再比对时间，判定属于「重复 / 冲突 / 改期」
3. **`POST /push`** —— 上面两关都过了才写入；判定为「改期」时带 `replace: true`。

最终由下游消费队列，同步进「提醒事项」。

### ❓ 未决：下游到底有几个消费者

- 本文档（依据用户的快捷指令截图）：**iPhone 快捷指令** `GET /claim` → 写「收集桶」
- Clawbot 早先的说法：**Mac / iPhone consumer 直接写入**
- 另有一个 **Mac 端程序在上传 `/snapshot`**（设备提醒快照）

三者可能并存，但**若快捷指令与 Mac consumer 都调用 `/claim`，两者会争抢同一批
条目**（认领即出队），可能导致部分提醒只落到其中一台设备。

**待确认**：Mac 端那个程序只上传 `/snapshot`，还是也会 `/claim`？
不影响写入，但影响简报准确性与「提醒会不会漏到另一台设备」。

## 铁律

1. **动手前先问「现在是怎么做的」**，不要假设用户没有方案。
2. 验证标准是**用户在 iPhone 上看得见**，不是 API 返回 200。
3. **查询只用 `/pending` 和 `/snapshot`**；`/claim` 是消费型，一读就把用户
   待收的提醒吃掉，任何情况下都不要拿它做调试或查询。
4. **写入前先走完去重协议**（`/pending` → `/snapshot` 相似度比对 → `/push`），
   不要拿到内容就直接 POST，否则会在用户设备上堆重复条目。
5. **不部署、不改配置、不重启该服务** —— 它是唯一送达通道。
6. 现役链路的任何一环变了，**回来改这份文件**。
